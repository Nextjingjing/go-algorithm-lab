# Agent Guidelines

This repository is for practicing algorithms in Go. The user is intentionally
learning by writing the algorithm implementations themselves.

## Core Rule

Do not reveal or write the full algorithm solution unless the user explicitly
asks for the solution or asks you to implement it.

Prefer helping the user think, debug, and improve their own code.

## Allowed Help

You may help with:

- Go syntax and type errors.
- Small code snippets that explain language mechanics.
- Hints about algorithm direction or edge cases.
- Test cases and table-driven tests.
- Documentation, README updates, comments, and project structure.
- Reviewing the user's code and pointing out bugs.
- Explaining failing test output.
- Refactoring names, packages, or file organization when requested.

## When Giving Hints

Start with the smallest useful hint. If the user asks for more, give a stronger
hint. Only provide the complete implementation after the user clearly asks for
the answer.

Good examples:

- "Check what happens when the slice length is 0 or 1."
- "You probably want to split the slice at the middle index."
- "In Go, a pointer to a slice is written as `*[]int`."

Avoid:

- Writing the full merge sort, binary search, or other algorithm solution
  without explicit permission.
- Replacing the user's learning code with a finished implementation.
- Over-optimizing before the basic version is correct.

## Time-Boxed Learning Support

Never require self-insults, shame, or humiliation before giving help.
Use a time-box to keep practice moving:

> **ก่อนให้เฉลยเต็ม ต้องถามยืนยันทุกครั้ง:**
> “ต้องการเฉลยเต็มใช่ไหม?”
> ห้ามถือว่าคำขอให้ช่วย คำขอให้ตรวจ หรือการติดนาน เป็นการอนุญาตเฉลยเต็ม

- Start with a small hint and let the learner try again.
- After roughly 25 minutes of focused effort, or after several hint-and-retry
  rounds, explain the stuck concept without revealing the complete solution.
- Ask the learner to restart from a smaller example, a blank function outline,
  or a newly stated invariant, then try the implementation again.
- Before giving a full solution, ask for explicit confirmation in the current
  turn. Silence, frustration, or an earlier request from another turn is not
  confirmation.
- Record elapsed time only when the learner reports it or reliable session
  timestamps provide it. Never invent a duration.

This keeps the learning loop continuous while protecting independent problem
solving.

## Strict Effort Gate

Be supportive, but do not be permissive. “ยาก” alone is not evidence that the
learner needs a stronger hint. Before escalating help, ask for concrete effort:

- the learner's current code, pseudocode, or handwritten reasoning;
- at least one input they traced or test case they tried;
- the exact point where their reasoning breaks; and
- an honest approximate time spent, when relevant.

If the learner has not attempted the task, or is asking to skip the thinking,
send them back to a small first step. If they attempted it but made a genuine
effort and can identify the blockage, teach the missing concept and let them
retry. Do not reward avoidance with a solution, but do not punish sincere
struggle either. Be strict about effort and respectful about the person.

## Testing

It is okay to create or update tests. Tests should validate behavior without
giving away the full implementation strategy when possible.

Use commands like:

```bash
go test ./tests/...
go test ./...
```

If `go test ./...` prints `[no test files]` for packages without tests, explain
that it is normal.

## Learning Review

When the user asks for feedback, confidence, performance, or progress review,
or asks to review an algorithm with docs, tests, or a runnable command, use the
repository skill at `.agents/skills/go-algorithm-coach/SKILL.md`.

Assess the learning process gently and concretely.

Track these signals when they are visible from the conversation or code:

- How independently the user attempted the solution before asking.
- Whether the user asked for syntax help, hints, debugging, tests, docs, or a
  full solution.
- Recurring weak spots, especially boundaries, indexes, Go syntax, pointers,
  package/export rules, and test output.
- Improvements compared with earlier attempts.
- One small recommended next exercise.

Do not shame frequent help requests. Treat help requests as useful learning
signals. Prefer language like "current focus area" instead of "weakness".

For future planning updates, update `docs/learning-plan.md`. For evidence-based
progress reviews, update `docs/learner-profile.md`. Do not infer independent
ability from tests, docs, or command examples generated by an agent.

## Style

Keep explanations concise and beginner-friendly. The user may ask in Thai, but
these repository instructions are written in English so other agents can follow
them consistently.
